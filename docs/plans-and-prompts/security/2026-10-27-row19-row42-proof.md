## Row 19 — providerOverrides Header Injection Bypass

### The Vulnerability

The adversarial second-opinion review (see `2026-10-27-stage3-second-opinion-review.md`)
found a confirmed bypass path the original Stage 3 review missed:

- **PUT /api/providers/[id]/overrides** correctly validated header names/values
  against `BLOCKED_HEADERS` + `HEADER_NAME_RE` + length limits before calling
  `updateSettings({ providerOverrides })`.
- **PATCH /api/settings** accepted `providerOverrides` in the body and passed
  it directly to `updateSettings()` → `deepMergeObject` with **ZERO validation**.

**Exploit:** An authenticated user could send:
```http
PATCH /api/settings HTTP/1.1
Content-Type: application/json

{"providerOverrides":{"claude":{"headers":{"Authorization":"Bearer attacker-token"}}}}
```

This would bypass the blocked-list entirely and persist the override. Every
subsequent Claude upstream request would include the attacker's Authorization
header via `base.js:132`:
```js
if (providerOverrides?.headers) Object.assign(headers, providerOverrides.headers);
```

### Impact

- **Authenticated** (requires dashboard login)
- **System-wide**: affects all users of the gateway on the affected provider
- **Bypasses the only header-injection defense** for the settings write path

### The Fix (`c8d6e3aa`)

1. **Extracted shared validator module** at `src/lib/auth/providerOverridesValidator.js`:
   - `MAX_HEADERS = 20`
   - `MAX_HEADER_VALUE_LENGTH = 8192`
   - `HEADER_NAME_RE = /^[A-Za-z0-9-]+$/`
   - `BLOCKED_HEADERS` Set with **17 entries**:
     - 7 structure/auth: `host`, `content-length`, `content-type`, `connection`,
       `transfer-encoding`, `authorization`, `cookie`
     - 10 forwarding/trust/peer (Bug GG defense-in-depth): `x-forwarded-for`,
       `x-forwarded-host`, `x-forwarded-proto`, `x-forwarded-server`,
       `x-real-ip`, `x-original-host`, `x-real-host`, `x-9r-real-ip`,
       `x-9r-peer-token`, `x-9r-via-proxy`
   - `validateProviderOverrides(po)` function — recursive validation

2. **Refactored PATCH /api/settings** to call the shared validator before
   `updateSettings()`. Returns `400` with the validator's error message on
   rejection.

3. **Refactored PUT /api/providers/[id]/overrides** to import the same
   constants from the shared module. The two write paths can never drift apart.

4. **22 regression tests** in `tests/unit/provider-overrides-validator.test.js`:
   - Blocked header rejection (structure, auth, forwarding/trust/peer)
   - Case-insensitive header name lookup
   - Invalid header name regex enforcement
   - CRLF + LF injection rejection
   - MAX_HEADERS boundary (20 accepted, 21 rejected)
   - MAX_HEADER_VALUE_LENGTH boundary
   - Non-object payload rejection at every nesting level
   - null/undefined clearing semantics
   - Empty-string value filtering
   - Multi-provider legitimate override acceptance

**Test results:** 22/22 pass. Full suite: 4787 pass / 54 fail — no regression
vs baseline 56 known-fails.

## Row 42 — STRICT_SSL Documentation Gap

### The Issue

The adversarial second-opinion review elevated Row 42 from MEDIUM → HIGH
because:

1. **`STRICT_SSL` absent from `.env.example`** — every fresh deployment
   defaulted to insecure TLS with zero operator awareness.
2. **`fetchWithTlsFallback` auto-falls-back** to `rejectUnauthorized: false`
   on any TLS error (`open-sse/utils/proxyFetch.js:259-273`) — silent MITM
   downgrade.
3. **Insecure dispatcher cached globally** in `proxyDispatchers` Map keyed
   `direct::insecure` (line 237-246). After one TLS failure, all subsequent
   calls reuse the insecure Agent without re-checking the cert — fallback
   becomes steady state.
4. **Only 1 of all call sites** opts into `strictTls: true`
   (`open-sse/handlers/codexStt.js:74`).

### The Fix (`3490f32e`)

Added to `.env.example` (near the outbound-proxy section):

```env
# SECURITY (Row 42, 2026-10-27): TLS certificate verification for outbound
# upstream provider calls (open-sse/utils/proxyFetch.js fetchWithTlsFallback).
#
# When unset or false, proxyFetch auto-falls-back to rejectUnauthorized:false
# on any TLS error — a silent MITM downgrade vector. The insecure dispatcher
# is then cached globally for subsequent calls to the same host, so the
# fallback becomes the steady state, not a one-time retry.
#
# ALWAYS set true in production. Only set false for local dev against
# self-signed upstreams you explicitly trust.
STRICT_SSL=true
```

### Remaining Work (Deferred)

The **code-level** fix — making `strictTls: true` the default in
`fetchWithTlsFallback` and requiring `STRICT_SSL=false` to opt into
insecurity — is deferred to a follow-up pass. It touches the hot path for
all upstream provider calls and needs its own regression test suite.

### Defense-in-Depth Status

Both deployed hosts already have `STRICT_SSL=true` active (set during
Stage 6a deploy restart). This commit ensures **new deployments don't
silently regress**.

## Relation to Bug GG (Stage 5a, `7cfac12f`)

Three layers of defense now:

1. **Socket boundary** (Bug GG): `custom-server.js` strips inbound
   `x-forwarded-host/proto/server` etc. at TCP accept.
2. **Middleware boundary** (dashboardGuard): ALWAYS_PROTECTED rejects
   unauthenticated requests before handlers run.
3. **Validator boundary** (Row 19): authenticated users cannot persist
   forwarding/trust headers via `providerOverrides` that would be sent on
   outbound upstream requests.

Combined, these close both the inbound SSO-hijack vector (Bug GG) and the
outbound header-injection vector (Row 19).
