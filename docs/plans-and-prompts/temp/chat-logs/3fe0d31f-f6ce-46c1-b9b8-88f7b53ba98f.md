1.  **Install Dependencies Natively**:
    *   **Neo4j**: Install via Homebrew (`brew install neo4j`) or download directly.

    *   Copy `.env.example` to `.env`.
    *   Update `NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD`, and `REDIS_URL` to point to your local native installations (e.g., `bolt://localhost:7687` and `redis://localhost:6379`).

    *   Install packages: `npm install`
    *   Build the project: `npm run build`
    *   Start the MCP server: `npm run dev` (for hot reload) or start the compiled server directly.

4.  **Production/Systemd**:
    *   The repo includes a `deploy/systemd/` directory with service files to run MemBerry, Neo4j, and Redis as system services outside of Docker containers.

### Key Considerations:
*   **Complexity**: Running without Docker requires manually managing three separate services (Neo4j, Redis, MemBerry Server) and ensuring they are all running and accessible.
*   **Ports**: Ensure ports 7687 (Neo4j), 6379 (Redis), and 3101 (MemBerry MCP) are open and not conflicting.

```bash
mkdir memberry-local && cd memberry-local
```

Instead of `brew install neo4j` (which installs globally), download the Neo4j Community Edition tarball/zip directly into this folder.

### 3. Install Redis Locally
Similarly, download a precompiled Redis binary or build it inside this folder.
- Download from [redis.io/download](https://redis.io/download/).
- Extract/build into `./redis`.
- Start it: `./redis/src/redis-server --dir ./redis-data` (specify a local data dir).

### 4. Clone and Configure MemBerry
```bash
git clone https://github.com/AP3X-Dev/memberry.git .
npm install
cp .env.example .env
```

Edit `.env` to point to your local instances:
```env
NEO4J_URI=bolt://localhost:7687
NEO4J_USER=neo4j
NEO4J_PASSWORD=<your-password> # Set this in neo4j/conf/neo4j.conf if needed
REDIS_URL=redis://localhost:6379
MCP_PORT=3101
MEMBERRY_API_TOKEN=<generate-a-random-token>
```

### 5. Run MemBerry
```bash
npm run build
npm run dev
```

### Cleanup
To remove everything, just stop the processes and delete the folder:
```bash
# Stop services
./neo4j/bin/neo4j stop
./redis/src/redis-cli shutdown

# Delete everything
cd ..
rm -rf memberry-local
```

### Why this works
- **Neo4j** and **Redis** are both portable; they don't require system-wide installation if you manage their binaries and data directories manually.
- **MemBerry** is a Node.js app; `node_modules` stays inside the folder.
- No global state is touched except for potentially open ports (which are released when processes stop).

This approach gives you the "easy to remove" benefit of Docker while running natively on macOS.

### How MemBerry Works
1.  **Graph-First Storage**: The primary source of truth is a **Neo4j graph database**. Entities (code symbols, concepts, people), relationships, episodic memories (session logs), and semantic principles are stored as nodes and edges in Neo4j.
2.  **Redis Caching**: Redis is used for high-speed caching, session locks, and temporary block storage to avoid hitting Neo4j for every read.
3.  **MCP Server**: A TypeScript server (`packages/mcp`) exposes this graph via 49 MCP tools. Agents call these tools to `load` context, `store` new learnings, or `query` the graph.
4.  **Wiki Compilation**: The `packages/wiki` module can **export** the graph into a static site of Markdown files. It walks the graph, renders nodes as Markdown with YAML frontmatter, and writes them to a directory. This is currently a **one-way export** (or a sync-back feature where edits to the wiki are pushed back to the graph).

### Can it store things in Markdown as well?
**Yes, but not natively as the primary source of truth.**

Currently, MemBerry has strong **Markdown serialization** capabilities:
*   `packages/core/src/markdown.ts` contains `renderToMarkdown()` and `parseFromMarkdown()` functions. These convert internal memory nodes (Semantic/Episodic) into Markdown files with YAML frontmatter and vice versa.
*   The Wiki compiler uses these to generate a browsable Markdown representation of your entire knowledge graph.

**To make it "Markdown-first" (file-based source of truth):**
You would need to modify the architecture significantly:
1.  **Replace Neo4j/Redis with File System**: Instead of saving nodes to Neo4j, the `MemoryBlockService` and graph stores would need to write/read `.md` files from a local directory.
2.  **Indexing**: You’d need a local indexer (like a simple SQLite DB or even just in-memory maps) to handle queries that Neo4j currently does (e.g., "find all entities related to X").
3.  **Concurrency**: File-based storage requires careful handling of concurrent writes (locking) which Neo4j handles automatically.

**Is it easy?**
*   **Moderate effort**: The serialization logic (`markdown.ts`) already exists. You wouldn't need to invent the file format.
*   **High effort**: Replacing the graph query engine (Neo4j) with a file-based alternative that supports complex relationship traversals ("who calls this function?", "what depends on this?") is non-trivial. You’d lose the powerful graph analytics unless you rebuilt them on top of file parsing.

**Recommendation:**
If you want a **file-based** memory system, MemBerry is overkill because its core value is the **graph**. If you just want to save memories as Markdown files, a simpler tool like [Mem0](https://github.com/mem0ai/mem0) (which supports vector + file storage) or a custom script using `llm-indexer` might be easier. However, if you love MemBerry’s features but hate Docker/Neo4j, you could theoretically fork it and swap the `neo4j` package for a `filesystem` package using the existing `markdown.ts` serializers.
